# Variant B — owner-controlled publication
Approved design only; activation, merge and deployment are not authorized.
The PR check is regression/classification only. It never grants deployment permission. The old gatePassed helper and Ed25519 verifier remain optional tested prototypes, not invoked by the active workflow. Remove the PR environment approval job to avoid duplicate approval and bootstrap deadlock. A green check is not consent to merge or publish.

## Activation sequence (owner, separately approved)
1. Record current main SHA, Pages source, existing successful deployment, live URLs and backup of the deployed artifact. Verify repository settings and owner-only reviewer availability. If the connector shares the owner identity, restrict its ability to merge, dispatch or administer through independently enforced permissions; otherwise the protection is against accidents only.
2. In an isolated disposable test environment, verify manual dispatch, rejection, cancellation, stale SHA, exact artifact identity, full browser/security regression and rollback. The current Pages example is not ready for activation: add the exact-SHA full regression requirement and validate the site allowlist. Do not deploy the example as-is.
3. Explicitly approve bootstrap PR #79 separately. Verify all required checks on its final SHA. Do not merge #78 as part of bootstrap. Since current Pages may auto-publish main, treat bootstrap merge as a potential production publication and require explicit consent.
4. Settings > Rules > Rulesets: target main; require PR, strict up-to-date status checks, conversation resolution, linear history, prohibit force pushes and deletion. No bypass where supported. Select unique, unconditional check names from actual completed runs, including release-gate; do not require ambiguous regression names or path-filtered jobs. Verify direct push denial using a disposable branch/ruleset first.
5. Settings > Environments > github-pages: require owner reviewer, restrict deployment to main, disable admin bypass where supported. Verify self-review behavior; do not enable prevent-self-review if it would make owner-only publication impossible. Ensure the assistant cannot approve as owner. If independent owner approval cannot be enforced, stop.
6. Settings > Pages: switch source to GitHub Actions only with explicit approval and a tested recovery plan. Install the reviewed production workflow, enable its variable only after verifying environment protection. All site publications, including preview, require owner approval initially. Preserve /moja-silownia/ and /moja-silownia/preview/. For staging-only publication assemble from last approved production artifact and validate unchanged production manifest; no automatic staging publisher is enabled.
7. Archive the exact deployed artifact, SHA-256 manifest, source commit, run/deployment ID and approval record in an owner-controlled release. Verify immutable releases availability; otherwise use an independently protected backup and do not treat mutable releases as trusted. No custom signing keys in variant B. Never store user training data in artifacts.
8. Verify live version, offline/cache, history isolation and both URLs; rollback only with explicit owner approval using the previous verified artifact. Record outcome.

## Limits
Same-origin staging is not a security boundary. PR code can alter its own checks. Owner-level credentials can bypass owner-controlled safeguards. The deployment template remains inactive and needs integration testing. No automatic staging publication, no production key generation, no settings changes.
